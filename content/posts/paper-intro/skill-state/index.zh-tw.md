## Agent 跑越久越貴：把對話歷史換成一份狀態

讓一個 AI agent 處理一個要走 200 步的倉儲任務：顧客下單、貨物上架、搬移貨架，一件接一件。現在幾乎所有 agent 都用同一套做法執行這種任務：每走一步，就把之前所有的觀察和思考接回 prompt，下一步整段重讀。於是執行越久，prompt 越長，花的錢和等待的時間跟著暴增。同樣 200 步，保留完整對話歷史的做法用掉 5,041,164 個 token，只留一份「倉庫現在長什麼樣」的狀態，只用 122,384 個，差了 41 倍。

可是準確率只是 0.94 對 0.88（只留狀態對保留歷史）。換到關聯密集的軟體版本庫環境，在 25 步長的任務上，只留狀態的做法還輸給保留歷史的對照組。**這篇論文省錢的證據很硬，變準的證據沒那麼穩**，而且不是每個環境都成立。

這是 Google 與 Purdue 的論文《SKILL.state: Scalable Long-Horizon Agent Skills》提出的做法。模型每一步只看三樣東西：任務指令、一份描述「世界現在長什麼樣」的結構化狀態、這一步的最新觀察。模型的思考過程用完就丟，只把「狀態該怎麼改」的結論留下來。這樣 prompt 大小就跟已經走了幾步無關，整體成本從隨步數平方成長，變成線性成長。

論文：[SKILL.state: Scalable Long-Horizon Agent Skills](https://arxiv.org/abs/2608.26263)（Google、Purdue）

## 對話式執行的兩個問題：越疊越長，舊資訊賴著不走

今天常見的 agent 做法叫 ReAct：模型每一步先寫一段推理、選一個動作，環境回傳觀察，這三樣都接到 prompt 後面，下一步再整段讀一次。模型每次呼叫時看得到的全部內容，叫做 [context](../../ai-concept/context-engineering/)。這種對話式執行有兩個具體問題。第一個是 prompt 長度隨執行步數增長，token 成本與延遲跟著漲：執行越久，context 裡塞的東西越多。

第二個問題是舊資訊會「賴著不走」，模型得自己分辨哪些還有效。早期的觀察、已經走過的推理，即使過期了也還留在 context 裡。模型每一步都要重新判斷「這段舊文字現在還算數嗎」，這本身就是額外負擔，也容易出錯：如果外部事件已經改變了世界，但舊的觀察紀錄還壓在上面，模型很可能照舊資訊做判斷。

舉個例子：context 前段寫著「shelf_42 放著 item_12」，後來有人把貨搬走了，這件事只出現在很後面的一句觀察裡。模型下一步要找 item_12 時，得自己判斷該信前面那句還是後面那句。

加上[記憶系統](../mem0/)（摘要、檢索）也沒有真正解決這兩個問題。這些方法本質上還是把過去的文字歷史重新整理一遍再餵回去，模型的決策仍然建立在「重建過去發生了什麼」，而不是「直接讀取現在世界長什麼樣」。執行的邏輯沒變，只是換了一種壓縮歷史的方式。

論文真正想回答的是：能不能把「現在的世界狀態」變成一個獨立於歷史文字、可以直接讀取的東西，讓模型不用每次都從一堆文字裡重建現況？

## SKILL.state 怎麼運作：每一步只看三樣東西

下面用論文附錄的倉儲情境當例子，貫穿整個機制：agent 管理一座倉庫的貨架，可用的動作只有 Store（上架）、Ship（出貨）、Move（搬移）、Wait（等待）。

### 三樣輸入、三樣輸出，狀態用合併來更新

每一步餵給模型的東西固定是三樣。\( P \) 是任務的固定指令（procedural specification），例如「你是倉儲管理員，可用動作是 Store/Ship/Move/Wait」，整個執行過程不變。\( \Sigma_t \) 是第 \( t \) 步當下的**結構化執行狀態**，一個 JSON 字典，記錄世界現在的樣子，例如「shelf_42 放著 item_12」。\( O_t \) 是這一步環境傳來的最新觀察，例如「Customer ordered item_12」。論文把這三樣合起來寫成 \( A_t \)：

$$
A_t = (P,\ \Sigma_t,\ O_t)
$$

圖 1 把兩種做法並排。左邊是傳統做法，prompt 裡除了指令和最新觀察，還疊著對話歷史、先前的觀察和推理；右邊是 SKILL.state，prompt 只有指令、狀態和最新觀察。下方的長條圖是重點：左邊的 context 一路變長，右邊維持在上限以內。

{{< image src="figure1.png" alt="左右對照的架構圖。左邊是傳統做法：prompt 依序放著任務指令、對話歷史、先前的觀察、先前的推理與最新觀察，交給模型執行動作。右邊是 SKILL.state：prompt 只放任務指令、執行狀態與最新觀察；模型的推理被劃掉，標示為用完即丟；一條標著 JSON Patch ΔΣ 的狀態更新箭頭繞回執行狀態。兩邊下方各有一張 context 成長長條圖，左邊標示持續變長，右邊標示有上限。" caption="圖 1 — SKILL.state 架構總覽：左邊的傳統做法 prompt 隨步數變長，右邊的 SKILL.state 維持固定大小（來源：原始論文 Figure 1。）" width="81%" >}}

模型看完這三樣，輸出三樣東西。\( R_t \) 是推理過程，也就是 chain-of-thought（模型一步步寫出來的思考），用完立刻丟掉，**永遠不會出現在下一步的 prompt 裡**。\( \Delta\Sigma_t \) 是狀態的「差異」，一個 JSON 字典，描述這一步要對狀態做哪些修改。\( a_t \) 是要執行的動作。

$$
(R_t,\ \Delta\Sigma_t,\ a_t)
$$

狀態的更新規則很單純。論文定義了一個運算子 \( \oplus \)，叫「帶 null 刪除語意的字典合併」：\( \Delta\Sigma_t \) 裡有的 key，直接覆蓋舊狀態裡同名 key 的值；某個 key 的值被設成 `null`，代表把它從狀態裡整個刪掉；\( \Delta\Sigma_t \) 沒提到的 key 維持原樣。寫成公式就是下一步的狀態等於這一步的狀態合併上差異：

$$
\Sigma_{t+1} = \Sigma_t \oplus \Delta\Sigma_t
$$

### 執行迴圈：推理用完就丟，狀態整份換掉

1. Runtime（負責呼叫模型、執行動作的外層程式）收到觀察 \( O_t \)。
2. 組成 prompt \( (P, \Sigma_t, O_t) \)，大小跟第幾步無關。
3. 模型輸出 \( (R_t, \Delta\Sigma_t, a_t) \)。
4. Runtime 檢查 \( \Delta\Sigma_t \) 的格式是否合法。合法就往下走；不合法就回滾，要求模型重新輸出。
5. 套用更新：\( \Sigma_{t+1} = \Sigma_t \oplus \Delta\Sigma_t \)。
6. 執行動作 \( a_t \)，\( R_t \) 永久丟棄。
7. 環境回傳新觀察 \( O_{t+1} \)，回到第一步。

拿傳統的 ReAct 式做法來對照，差別在 prompt 怎麼長：

```text
傳統做法：
  第1步 prompt: [P] + [O_1]
  第2步 prompt: [P] + [O_1, R_1, a_1] + [O_2]
  第3步 prompt: [P] + [O_1,R_1,a_1] + [O_2,R_2,a_2] + [O_3]
  ...越疊越長

SKILL.state：
  第1步 prompt: [P] + [Σ_1] + [O_1]
  第2步 prompt: [P] + [Σ_2] + [O_2]
  第3步 prompt: [P] + [Σ_3] + [O_3]
  ...大小大致固定（Σ 可能隨任務複雜度緩慢變化，但跟走了幾步無關）
```

傳統做法每一步都在 prompt 後面**加一段新的**，SKILL.state 每一步都把狀態**整份換掉**。

### 走一遍倉儲出貨的一步

論文附錄用這個倉儲情境示範一次出貨的完整流程，讀起來比公式直觀。開始時，item_12 放在 shelf_42。Runtime 收到觀察 \( O_t \)：「Customer ordered item_12.」（顧客訂了 item_12。）

模型內部的推理大概是：「顧客訂購了 item_12，我需要出貨。查看目前狀態，item_12 在 shelf_42。我要下 Ship 動作，並把狀態裡 shelf_42 的紀錄清掉。」這段推理之後會被丟掉。模型實際輸出的是這個 JSON：

```json
{
  "state_patch": { "inventory": { "shelf_42": null } },
  "action": "Ship item_12 shelf_42"
}
```

`state_patch` 就是 \( \Delta\Sigma_t \)，它把 shelf_42 設成 `null`；`action` 是 \( a_t \)。套用 \( \oplus \) 前後，狀態裡的 inventory 變成這樣：

| 貨架 | 套用前 | 套用後 |
| --- | --- | --- |
| shelf_42 | "item_12" | null（被刪除／清空） |
| shelf_43 | "item_9" | "item_9"（沒被提到，維持原樣） |

環境執行完動作，回傳新觀察 \( O_{t+1} \)：「Success: Shipped item_12 from shelf_42.」下一輪的 prompt 就是 \( (P, \Sigma_{t+1}, O_{t+1}) \)。推理過程 \( R_t \) 沒有出現，上一步的觀察 \( O_t \) 也沒有出現：模型只看到現在的狀態和最新的觀察，沒有半點歷史文字。

### 狀態欄位按 domain 設計一次

狀態要記哪些欄位，也就是狀態的 **schema**，是為整個 domain（同一類任務）設計一次，不是每個任務各設計一套。例如 InterCode CTF（100 道 Linux 解謎題，agent 要下 bash 指令找出藏起來的 flag 字串）的題目五花八門，涵蓋逆向工程、鑑識、密碼學、二進位漏洞利用，卻全部共用同一組欄位：已找到的 flag、已試過的假設與指令、目前操作的檔案、目前工作目錄、指令執行摘要。好處很直接：不用每個任務重新設計狀態格式，不同任務還能共用同一套 runtime 程式碼。

前提是這個 domain 事先就知道該追蹤哪些欄位。如果 schema 沒辦法事先固定、必須邊執行邊發現該追蹤什麼，這套做法就不適用。這是論文在 Limitations 一節自己承認的第一個失效情境。

### 驗證擋得住格式錯誤，擋不住語意錯誤

Runtime 在套用 \( \Delta\Sigma_t \) 之前會先做格式驗證：是不是合法的 JSON、key 的結構符不符合預期。驗證失敗就回滾重試，狀態退回上一步，要求模型重新輸出。所以格式錯誤的輸出不會污染狀態。

{{< admonition warning "格式對、內容錯的 patch 會被照單全收" >}}
驗證擋得住「格式不合法」，擋不住「格式合法、但語意錯誤」的輸出。比方說模型輸出一個會誤刪重要資訊的 patch，格式完全沒問題，驗證抓不到，錯誤的更新就被「成功」套用了。更關鍵的是，舊狀態已經不在 context 裡，一旦錯誤的 patch 被合法套用，就沒有回頭看歷史文字來自我修正的機會。相對於保留完整歷史的做法，這是整個架構在結構上更脆弱的地方。這不是猜測：論文自己的實驗顯示，小模型 68% 的失敗正是這種「語意上合法但錯誤的更新被無感套用」，後面談失敗模式時會回到這個數字。
{{< /admonition >}}

## 總成本為什麼從平方降到線性

論文用 \( T \) 代表總執行步數，比較兩種做法加總起來的 token 量級。量級寫成 \( O(\cdot) \)，意思是「\( T \) 變大時大致怎麼成長」，不管前面的常數。傳統做法第 \( t \) 步的 prompt 記作 \( C_t \)，長度 \( |C_t| \) 跟 \( t \) 成正比，是 \( O(t) \)。SKILL.state 第 \( t \) 步的 prompt 記作 \( P_t \)（注意不是前面的任務指令 \( P \)），長度是 \( O(|P|+|\Sigma|+|O|) \)，也就是指令、狀態、觀察三者的長度相加，跟 \( t \) 無關。把 \( T \) 步全部加起來，傳統做法是 \( T \) 的平方量級，SKILL.state 只是 \( T \) 的量級：

$$
\sum_{t=1}^{T} |C_t| = O(T^2) \qquad \sum_{t=1}^{T} |P_t| = O(T)
$$

用數字驗證直覺比較好懂。假設走 10 步，把每一步的長度簡化成「單位長度」：傳統做法是 1, 2, 3, ..., 10，SKILL.state 是 1, 1, ..., 1。傳統做法加起來是 \( 1+2+\cdots+10=(1+10)\times10/2=55 \)，這是等差數列求和，量級是 \( T^2 \)；SKILL.state 是 10 個 1 相加，\( 1\times10=10 \)，量級是 \( T \)。每一步的長度隨 \( t \) 線性增加，把這些線性增加的量再加總一次，就變成平方量級。

「1 單位」是簡化。SKILL.state 每一步的大小其實是 \( |P|+|\Sigma|+|O| \)，狀態 \( \Sigma \) 可能隨任務複雜度慢慢變大，例如關聯密集的環境裡，狀態會隨分支、PR 數量增加而變胖。但它的變化只跟「當下世界有多複雜」有關，跟「已經走了幾步」無關，所以說每步 \( O(1) \)、總和 \( O(T) \)，而不是每步剛好等於某個固定常數。

實測數字也對得上。後面的 Table 1 裡，\( T \) 從 100 加倍到 200 時，Stateful 對照組（同樣有結構化狀態，但還保留完整對話歷史）的總 token 成長了約 4.7 倍，接近理論預期的 4 倍（\( 2^2 \)）；SKILL.state 只成長約 1.9 倍，接近理論預期的 2 倍（\( 2^1 \)）。

## 實驗怎麼設計：測試環境與對照組

### 測試環境與計分方式

論文的測試分成兩類：自己設計的合成測試台 SkillExecBench，以及兩個別人設計的公開 benchmark。

**SkillExecBench** 是控制型的診斷測試台：世界怎麼變化由固定規則決定，用來把「執行機制本身」和「開放式的摸索搜尋」分開測。它可以把任務長度，也就是要走幾步（論文稱為 horizon），從 \( T=10 \) 一路拉到 \( T=200 \)。底下分成倉儲和軟體版本庫：

- 倉儲管理：500 個獨立、互不重疊的貨架，動作只有 Store/Ship/Move/Wait，測模型能不能在長時間執行中維持大量互不干擾的狀態變數。
- 軟體版本庫：Git 分支、commit、PR、CI 狀態彼此深度關聯，動作包括 CherryPick、Merge、RunTests、CreateRelease、Rollback。特色是「密集依賴」：單一動作（例如合併一個 PR）會連帶影響目標分支和其他相依的 PR，測模型能不能在互相糾纏的關聯圖上做結構化推理。

兩個公開 benchmark 是 **InterCode CTF**（Yang et al., 2023）和 **Sierra τ-Bench**（Yao et al., 2024）。InterCode CTF 就是前面提過的 100 道解謎題，涵蓋逆向工程、鑑識、密碼學、二進位漏洞利用，agent 在 Docker 容器裡執行 bash 指令，反覆測試假設找出隱藏的 flag。τ-Bench 測企業客服情境裡工具、agent、使用者三方的互動，分零售和航空兩個領域：agent 要跟模擬使用者對話、透過工具查詢 SQLite 資料庫，並在商業政策的限制下執行交易。

三個環境的算分方式不同：SkillExecBench 是連續分數（成功的動作數除以總事件數）；InterCode CTF 用 pass@1，也就是第一次嘗試就解出來的比例；τ-Bench 用官方評分器檢查資料庫的最終狀態。除了準確率，論文也記錄每次呼叫 LLM 的平均 prompt 大小，以及整個執行過程累積的 token 總量。

### 對照組：關鍵是 Stateful 與預算對齊組

架構層面的對照組有三個。**Prompt(ReAct)** 是最原始的做法，每一步的觀察、推理、動作全部往後疊加。**Memory(Summary)** 保留最近三輪的原文，再加上一份定期更新的自然語言摘要。**Stateful(LangGraph)** 仿照 LangGraph（一個 agent 開發框架，可以在對話之外維護一份結構化狀態）的做法，有結構化的狀態區塊，但**同時**保留完整的滾動對話紀錄。

Stateful 是最關鍵的對照組。它跟 SKILL.state 一樣有結構化狀態，唯一的差別是「狀態加完整歷史並存」還是「只有狀態，歷史全丟」。只有這一組比較，才真正驗證了「丟掉歷史」這個決定有沒有價值；其他對照組頂多證明「結構化狀態比純文字歷史好」。

論文另外設了一組**預算對齊控制組**，專門排除「贏只是因為 prompt 比較短」這個可能。三種做法都把 prompt 硬壓到跟 SKILL.state 差不多短：Truncated(Sliding Window) 只留最近幾輪，硬卡 token 上限；Summary-capped 用自然語言摘要，但嚴格限制摘要本身的長度；ReAct+LLMLingua 用 LLMLingua 壓縮，這個工具讓一個小模型依困惑度（小模型覺得一段文字有多難預測）刪掉它認為不重要的字，硬壓到目標 token 數。

模型用了 Gemini-3-Flash（不公開權重）、Gemma-4-31B-it 和 Qwen-3-8B-it（公開權重），溫度設 0.0（每次輸出盡量固定）。合成實驗跑 5 個隨機種子，\( T \geq 50 \) 時做 paired t-test（一種檢查差距是不是隨機波動的統計檢定），論文聲稱 \( p<0.01 \)。

## 看數字前的保留：長任務只在自建環境測過

SkillExecBench 刻意把任務長度從 \( T=10 \) 掃到 \( T=200 \)，是明確的長度掃描。但 InterCode CTF 和 τ-Bench 兩節，論文完全沒有報告一個任務平均要走幾步。如果這些任務平均 10 到 20 步就結束，「公開驗證」就根本沒有測到 SKILL.state 宣稱最擅長的長任務；真正對長任務做過壓力測試的，只剩論文自己設計、自己控制的合成環境。

業界其實有專門測長任務、真實世界 agent 能力的公開 benchmark，這篇論文一個都沒用：

- SWE-bench：修真實 GitHub issue 的任務，往往需要數十到上百輪工具呼叫。論文自己的軟體版本庫環境本質上就在模仿這類任務，卻選擇自己造一個簡化版，而不是直接用真的 SWE-bench。
- WebArena / Mind2Web：長距離的網頁操作任務。
- GAIA：需要多步驟串接工具推理的通用助理任務。
- OSWorld：真實作業系統的操作任務。

論文沒有解釋為什麼不用這些更有代表性的長任務 benchmark。這不代表論文的數字是假的，而是「長任務的做法在真實世界也成立」這個宣稱，證據比表面看起來薄：最有說服力的長任務數字，全部來自自己設計、自己控制的合成環境。讀後面的結果時，這個保留值得放在心裡。

\( T=10 \) 時 Stateful 和 SKILL.state 都是 \( 1.00\pm0.00 \)，打平。到了 \( T=25 \)，SKILL.state（\( 0.88\pm0.08 \)）反而**輸給** Stateful（\( 0.94\pm0.03 \)）6 個百分點。\( T=50 \) 才贏回來（0.86 對 0.74），\( T=100 \) 領先擴大到 15 個百分點（0.78 對 0.63）。

{{< admonition warning "這個反例跟論文自己的宣稱矛盾" >}}
論文摘要說 SKILL.state「improves task accuracy... across diverse datasets」，正文說它「matches or exceeds baseline accuracy across all horizons」。但「across all horizons」只在倉儲環境成立，換到軟體版本庫就有 \( T=25 \) 這個反例，論文正文完全沒有提到。SKILL.state 在這張表的標準差也偏大（\( \pm0.08 \)），結果不算穩定。
{{< /admonition >}}

我的推論是，這跟軟體版本庫的密集依賴有關。單一動作可能連帶影響多個分支；一旦某次 patch 沒有正確捕捉到連帶影響（例如合併了 PR，卻漏了更新相依分支的狀態），錯誤可能一路延續到後面的步驟，因為沒有原始歷史文字可以回頭核對。這正好是前面說的驗證盲區，\( T=25 \) 的反例很可能就是這個風險真的發生了。

「準確率全面提升」會隨環境的關聯密度出現反例；跨所有環境都穩定成立的優勢，只有 token 節省。

## 它會在哪裡失敗：小模型的錯誤與三種失效情境

換成公開權重的 Gemma-4-31B，SKILL.state 在 \( T=100 \) 的倉儲任務上準確率只剩 0.42。其他做法在同一長度的分數，可以在下面的表 7 對照。

{{< image src="table7.png" alt="表格，列出 Gemma-4-31B 在四種任務長度下，Prompt、Memory、Stateful、SKILL.state 四種做法的準確率、平均 prompt 與總 token，各附標準差。" caption="表 7 — 換成 Gemma-4-31B 跑倉儲環境的 scaling 結果（來源：原始論文 Table 7。）" width="82%" >}}

論文把失敗案例分了類：

| 失敗類型 | 具體是什麼 | 占比 |
| --- | --- | --- |
| Premature State Overwrite/Deletion | 合併時不小心漏掉既有的 key，等於誤刪 | 68% |
| Schema Comprehension/Type 錯誤 | 巢狀的 list 和 dict 搞混 | 20% |
| JSON 語法／格式錯誤 | 漏逗號、括號沒對齊 | 12% |

論文的結論是：小模型失敗的根源是**結構化輸出的遵從度**（能不能照規定的格式和結構正確輸出），不是推理能力不足。

我的推論是，第一類的 68% 就是前面那個驗證盲區的直接證據：語意上合法、但錯誤的 patch 被套用之後，沒辦法回頭校正。它跟軟體版本庫 \( T=25 \) 的反例，本質上是同一個問題的不同表現。

整套設計依賴一個前提：**執行狀態可以成為未來執行的充分統計量**。意思是過去發生的一切，只要當下就被正確寫進狀態，就不需要保留原始文字。論文自己承認，這個前提在三種情境下會失效：

1. **Schema 沒辦法事先固定**：必須邊執行邊發現該追蹤哪些欄位。
2. **某個早期觀察，當下沒被判斷為重要，後來才發現有關**：因為沒寫進狀態，事後也找不回來。這是三者中最現實、最容易在正式環境踩到的一項。整個架構最根本的賭注，是賭模型在**當下**就能做出正確的取捨，一旦賭錯，沒有回頭路。
3. **任務的目標就是歷史軌跡本身**：例如稽核、debug 溯源、解釋過去做了什麼決策。這種任務下，丟掉歷史直接跟任務目標衝突。

論文另外承認兩個附帶限制。多個 agent 共享同一份狀態時，同時寫入會衝突，論文只說「可以自然擴展」，沒有實作也沒有測試。grammar-constrained decoding（生成時直接限制模型只能輸出符合語法的內容）可以消除上面第三類的純語法錯誤，但解決不了第一類的語意錯誤。

## 實務上該選 ReAct 還是 SKILL.state

一個常見的直覺是：保留過去的動作紀錄比較有容錯空間，對強模型來說應該利大於弊。這個「容錯」其實有兩種意義，要拆開看。

第一種是事後可以追溯、可以除錯。這方面保留歷史確實佔優勢，出錯後還能回頭檢查原始資料；SKILL.state 一旦把資訊丟掉，就真的回不去了，也就是上一節的第二種失效情境。

第二種是長任務的準確率會不會因為保留歷史而更穩。前面 Table 1 的數字反駁了這個直覺：即使用論文測過最強的模型 Gemini-3-Flash，保留完整歷史的 Prompt(ReAct) 準確率還是從 0.90 一路跌到 0.74，標準差還放大了 7 倍。

論文引用 lost-in-the-middle 現象（Liu et al., 2024）來解釋長 context 的準確率退化：模型技術上看得到長 context 裡的資訊，不代表能可靠地用到。我的推論是，這不是推理能力不夠，所以換成更強的前沿模型，這個弱點也不會消失，只是程度可能緩和。「強模型加保留歷史，利大於弊」在短中距離的任務成立，在長任務上則被實測數據推翻。

把這些線索整理成一張決策表：

| 軸線 | 傾向 ReAct（保留歷史） | 傾向 SKILL.state（丟棄歷史） |
| --- | --- | --- |
| 相關性何時能判斷 | 事後才發現某個觀察有用（debug、探索式研究） | 當下就能判斷這筆該不該記（倉儲、資料庫狀態這類） |
| 軌跡本身是不是產出物 | 是（稽核、合規、解釋過程） | 否（只要最終狀態或結果對） |
| 狀態的關聯密度 | 密集互相依賴（Git 圖、連鎖財務計算） | 稀疏獨立（像 500 個互不相關的貨架） |
| 預期執行長度 | 短到中（關聯稀疏時約 25 步以內）：兩者準確率打平，ReAct 比較簡單 | 長（100 步以上）：保留歷史的做法準確率退化、變異放大，狀態型維持穩定 |
| 模型能力 | 弱模型：合法但語意錯誤的 patch 被無感套用是重大風險 | 強模型能降低這個風險，但前沿模型只是沒測過，沒有證據顯示完全免疫 |
| 對成本／延遲的敏感度 | 不敏感（呼叫次數少、預算充足） | 敏感（高頻呼叫、要上正式環境） |

關聯密集時，patch 一旦出錯，後果會無聲擴散，而且無法回頭比對原文；關聯稀疏時，錯誤的影響範圍被限制住。「25 步以內打平」也只適用於關聯稀疏的環境，關聯密集時這條線會更早出現，例如軟體版本庫在 \( T=25 \) 就已經反過來輸。短到中的任務選 ReAct 的好處，是不用多蓋一層 schema 和驗證的基礎設施；成本敏感的場景則是因為 \( O(T^2) \) 的成本會爆表。

{{< admonition tip "先問這一句" >}}
這個 domain 的狀態，我能不能在事情發生的當下就決定該不該記？如果能（結構清楚、關聯稀疏、任務夠長），選 SKILL.state；如果不能，或需要稽核軌跡，或狀態關聯密集，優先考慮 ReAct，或「狀態加有限歷史」的混合做法。
{{< /admonition >}}

介於兩者之間的，是 Table 1 和 Table 6 裡的 Stateful 對照組，LangGraph 風格的「結構化狀態加完整對話歷史」。它不是純 ReAct，也不是 SKILL.state 那種只留狀態，而它在軟體版本庫 \( T=25 \) 時甚至贏過 SKILL.state，就是前面那個 Stateful 0.94、SKILL.state 0.88 的反例。

我的推論是，如果不確定「當下就能正確判斷什麼該記」這個假設成不成立，「狀態加一小段近期歷史」的混合做法，可能比論文給的兩個極端都務實：有把握的部分交給結構化狀態，同時留一小段滾動歷史當安全網，萬一 schema 漏掉了什麼，近期歷史還能補救。成本介於兩者之間，不是每步 \( O(1) \)，但也不會一路線性疊加到底。

## 結論：省成本可以期待，全面變準還不行

這篇論文的工程價值很高，尤其在成本上；研究上的新意則中等偏低。它最紮實的部分，是把「結構化狀態加丟棄歷史」系統化，並給出 \( O(T) \) 對 \( O(T^2) \) 的複雜度證明。但核心概念早就存在：[MemGPT](../memgpt/)（讓 LLM 自己管理長期記憶的系統）、LangGraph 的狀態區塊，以及 Dialogue State Tracking（對話系統裡追蹤使用者需求的技術）都做過類似的事，論文的貢獻是證明和系統化衡量，不是提出新概念。預算對齊控制組這個實驗設計也值得記住：它證明贏的是「結構化」，而不只是「變短」，這個方法論比論文的核心主張更值得留在腦子裡。

SKILL.state 用一個簡單的想法解決一個很具體的問題：把「現在的世界狀態」和「歷史文字」分開，prompt 就不再隨步數變長。把它當成省成本的解法來考慮，證據很夠（\( T=200 \) 時省 41 倍）；當成全面比較準的解法來期待，證據還不到那個程度，軟體版本庫 \( T=25 \) 的反例就是最直接的證據：關聯密集的任務，加上驗證擋不住的語意錯誤，是這個架構真正的軟肋。論文常把準確率和成本包裝成同一個賣點，但兩者的證據力不對等。讀任何宣稱「又快又準」的論文，都可以把兩個宣稱拆開分別檢查，通常其中一個會明顯比另一個強。

要不要丟掉歷史，關鍵問題不是模型夠不夠強，而是**相關性能不能在資訊出現的當下就被正確判斷**。架構如果拿掉了「回頭核對原始資料」這條路，就等於把賭注全押在當下的判斷上。任何為了效率丟掉原始資料、只留摘要或萃取結果的系統，都在做同一種賭注，所以比論文結論本身更值得留下的，就是這個問題：它不限於 agent 設計，值得在任何「要不要丟棄原始資料」的系統設計裡重新問一次。

讀這篇論文，還能順手帶走幾個判斷習慣：

- 找全稱宣稱的反例：看到「across all X」，就去找跨資料集或跨環境的反例，像軟體版本庫的 \( T=25 \)。全稱宣稱通常只在最有利的環境成立，附錄或次要表格反而常藏著誠實的反例。
- 看得到不等於用得到：lost-in-the-middle（Liu et al., 2024）說的是模型能不能用上長 context 裡的資訊，這跟模型強弱是兩個獨立的維度，值得另外深入了解。
- 歷史要不要跟狀態並存：Dialogue State Tracking 是狀態加完整對話歷史並存，這篇是只留狀態。設計任何結構化狀態的系統時，先問這個子問題，而不是只把「有沒有結構化狀態」當成唯一的分類。
- 驗證只擋得住格式：論文自己的實驗（68% 的錯誤來自語意合法但錯誤的 patch）暴露了這一點，論文卻沒有明講它對架構的含義。任何「LLM 產生結構化輸出、程式自動套用」的設計，都要記得驗證擋不住「格式對、內容錯」。

如果你正在做會跑很久的 agent，可以先替自己的 domain 列一份狀態欄位，再找出哪些資訊沒辦法在出現的當下決定該不該記：那些地方，就是你還需要保留歷史的地方。
